# Research digest: tooling for a mechanics-first railroad tycoon game (2026-11-05)

Produced by five researchers and two adversarial fact-checkers. Where a fact-check CORRECTS a claim in a report, the fact-check wins.


# PART A - FACT-CHECK RESULTS (read first)


## Fact-check: tools

**Overall:** The three reports are factually reliable on versions and dates. I re-checked about 75 version, date, maintenance and capability claims against PyPI JSON, GitHub feeds and source files, crates.io, the Godot, Qt, Unity and Apple docs, and the local machine. About 85% were exactly right. Every headline version checked out: Arcade 3.3.3 and 4.0.0.dev8, imgui-bundle 1.93.0, pyglet 2.1.19 and 3.0.dev11, pygame-ce 2.5.8, raylib 6.2.0.0, Pyxel 3.0.0, PySide6 6.12.0, Dear PyGui 2.3.1, NiceGUI 4.0.0, Flet 1.1.0, Godot 4.7.2 and 4.8 beta 2, Bevy 0.20.1, Defold 1.14.0 and gdUnit4 6.2.3. No maintenance rating is wrong, but three need context: Kivy and LÖVE are slow only in releases (their main branches are active), and Dear PyGui is effectively minimal.

The errors that matter for the decision are about framing, not version numbers:
1. Both Python reports present wgpu as a ready Metal escape hatch, but released wgpu is incompatible with imgui-bundle 1.92.900 and later. Today the recommended Python stack is OpenGL-only on macOS.
2. python2d implies Godot shares the same OpenGL fragility, but Godot projects default to Metal on Apple Silicon. That strengthens the engines report's pick more than the engines report itself said.
3. python2d calls Python 3.14 'blocked' for Arcade 3.3.3, but Arcade officially supports 3.14; pymunk simply compiles from source.
4. The engines report's i7 data point comparing GDScript and Python is invalid: it pairs a debug build with a different machine.
5. pygui's '5-year LTS' for PySide6 applies to commercial licensees, not free users.
6. python2d's 8/10 for Arcade + ImGui rests on an untested integration through backends the maintainer calls a work in progress. pygui's advice to host in Hello ImGui is better supported.

Confirmed dealbreakers for this project: Textual, Pyxel, py4godot, godot-python, Unity's Python Scripting, pygame_gui (stagnant and no tables), and arcade.gui as the main panel UI (no tables). Nothing in the two leading routes is a dealbreaker today:
- **Python + imgui-bundle** runs in Hello ImGui/immapp with exact version pins, the map drawn in ImPlot, and the simulation in a UI-free package. It is defensible for a Python developer focused on mechanics. But it is a bet on OpenGL on macOS and on a single maintainer, with no working Metal fallback in released packages, and its Mac builds are Apple Silicon-only.
- **Godot 4.7 + typed GDScript** is the more robust platform for shipping a game: Metal by default, universal export, MIT licence and a large team. The costs are a new language, sortable tables and charts built by hand, and a Python prototype that has to be ported.

Recommended next step: all three reports agree on writing the economy simulation first as a headless, deterministic, tested pure-Python package. Before that, update Python from 3.13.0 to 3.13.18 and uv from 0.8.3 to 0.13.7. Then spend 1–2 days testing imgui-bundle with ImPlot on this Mac. Choose between Python and Godot based on that test and on whether you are willing to learn GDScript.

### Contradictions between reports

- Overall stack: python2d and pygui pick Python + imgui-bundle, while engines picks Godot 4.7 + typed GDScript. The verified facts cut both ways, and neither report states the trade-off fully. On the Python side, every recommended stack draws through OpenGL on macOS today (imgui-bundle forces GLFW+OpenGL3, and released wgpu breaks with imgui-bundle 1.92.900 and later). imgui-bundle's macOS wheels are arm64-only, and it has one maintainer who ships breaking point releases. On the Godot side, projects default to Metal on Apple Silicon, export as universal apps and are backed by a large MIT project, but the user must learn a new language and build sortable tables and charts themselves. Neither route has a dealbreaker: the engines report understated Godot's platform advantage, and the Python reports understated their stack's platform risk.
- Where ImGui should run: python2d recommends Arcade 3.3.3 plus imgui-bundle's pure-Python pyglet backend (fit 8/10). pygui rates the pure-Python backends over pyglet/Arcade/pygame at 4/10 and says to host everything in the Hello ImGui runner. pygui is better supported. imgui-bundle's own docs say the pure-Python backends have no Hello ImGui DPI, theme or asset handling and are 'largely a work in progress' (modifier keys are incomplete). No Arcade integration exists, and the only Arcade+ImGui package (arcade-imgui) requires Python <3.12. python2d's statement that the pyglet backend is official is true, but it overstates how mature it is.
- Python 3.14: python2d says Arcade 3.3.3 is 'blocked' on 3.14, but Arcade's own 3.3.3 changelog says 'Support for Python 3.14'. Arcade is right in principle, because pymunk 6.9.0 ships an sdist that compiles with Xcode CLT. python2d is right that there are no prebuilt cp314 pymunk wheels. Both reports' advice to use 3.13 stands. Python 3.15, now released, makes Arcade 3.3.3 harder still: its pillow~=11.3.0 pin has no cp315 wheels.
- Mac architecture standard: engines calls py4godot a dealbreaker partly because it is macOS arm64-only and so cannot ship a universal build. python2d and pygui recommend imgui-bundle without mentioning that its 1.93.0 macOS wheels are also arm64-only (macOS 14+); Dear PyGui is arm64-only too. Apple has said macOS 26 is the last release for Intel Macs, so arm64-only is acceptable for a game shipping in 2027 or later. py4godot's real dealbreaker is its alpha status and the README's 'demo' warning.
- Godot and the macOS 15.8.2 OpenGL regression: python2d lists Godot among the apps the RC blanked, as evidence that OpenGL is fragile. The Godot issue (#124311) involved only the Project Manager, which is the only part of Godot that defaults to OpenGL. Projects default to Forward+ on Metal, and launching with --rendering-driver metal worked around the bug. The episode therefore supports the engines pick rather than counting against it.
- How to draw the map: python2d plans an Arcade SpriteList for terrain plus a ShapeElementList for track. pygui plans to draw the whole map inside an ImPlot plot (PlotImage, a Segments-flag PlotLine and PlotScatter). Both rest on APIs that exist (checked in arcade's source and implot.h), and neither is benchmarked at the stated scale. The ImPlot route avoids the untested Arcade+ImGui glue, so it is the lower-risk first spike, with pyglet/Arcade as the fallback.
- imgui-bundle backend list: python2d lists pygame among the pure-Python backends. imgui-bundle's backends Readme says only glfw, sdl2, sdl3 and pyglet are implemented, although pygame_backend.py and a pygame example do exist. The Readme looks stale; treat the pygame backend as the least mature.
- pygame-ce and Metal: python2d says pygame-ce's docs state that its normal display path presents through Metal. That docs sentence describes the experimental pygame._sdl2.video Renderer class. pygui's point that ImGui forces pygame into OPENGL mode is correct and agrees with python2d's own caveat.

### Gaps

- None of the reports noted that Godot projects default to the Metal rendering driver on Apple Silicon. OpenGL is used only by the Compatibility renderer and the Project Manager. That removes, for Godot, the OpenGL-deprecation risk that hangs over every Python option.
- The wgpu/Metal escape hatch for imgui-bundle is broken in current releases. wgpu 0.32.0 calls ImDrawData.cmd_lists_count, which imgui-bundle 1.92.900 removed, and the fix has been on wgpu-py main since 2026-08-19 without a release. Today the Python stack has no working non-OpenGL path on macOS short of git installs.
- Mac CPU architecture is never checked for the Python stacks. imgui-bundle 1.93.0 (macOS 14+) and Dear PyGui 2.3.1 ship only arm64 macOS wheels, while pygame-ce ships universal2 and raylib ships both architectures. A PyInstaller .app built on imgui-bundle will run only on Apple Silicon.
- The user's toolchain is stale: python.org Python 3.13.0 (latest 3.13.18) and uv 0.8.3 (latest 0.13.7). Python 3.15 has also been released. imgui-bundle and pygame-ce already ship cp315 wheels, but Arcade 3.3.3's pymunk and pillow pins do not.
- This Mac runs 15.8.1. The 15.8.2 OpenGL regression was in RC1 and RC2 and fixed in RC3, and it is not confirmed whether the final 15.8.2 has shipped. GLFW and pyglet both go through NSOpenGLContext, so any OpenGL stack should be re-tested after updating.
- On Qt licensing, the free (open-source) PySide6 build receives only the first LTS patch releases, not 5 years of maintenance. The PySide6 analysis also misses Qt Quick/QML (LGPL), which renders through RHI to Metal or Direct3D 11 by default in Qt 6 and is a GPU path for the map.
- Shipping on Windows: PyInstaller executables are often flagged by Defender as Wacatac (pyinstaller#5854). This applies to the recommended Python stacks, not only the Godot+Python hybrid, so budget for code signing and early antivirus testing.
- No report sizes the Python simulation itself for fast-forward with many cities, industries and trains. PyPy is ruled out because imgui-bundle has no PyPy wheels, and there are no free-threaded wheels either. The realistic speed-ups are numpy vectorisation, a deterministic headless tick, and a compiled core later (Rust via PyO3/maturin, or Cython).
- Whether the game will be sold changes several choices, and none of the reports asks. Rider's free licence is non-commercial only. Qt Graphs and Canvas Painter are GPL or commercial. ImGui Test Engine has its own non-MIT licence. Apple notarization costs US$99/yr with any engine.
- Arcade is stuck between versions. The stable 3.3.x line has had no release for 13 months while work goes into 4.0 dev builds on pyglet 3.0 dev, and there is no announced date for either final. Starting on 3.3.3 means a forced migration partway through the project.

### Gap notes

### 1. Godot draws through Metal on Macs, Python stacks through OpenGL
- In Godot's project settings, `rendering/rendering_device/driver.macos` defaults to **metal** on Apple Silicon; Intel Macs fall back to Vulkan. The Compatibility renderer uses native OpenGL 3.3, with ANGLE optional. ([ProjectSettings.xml](https://raw.githubusercontent.com/godotengine/godot/master/doc/classes/ProjectSettings.xml), [Godot 4.4 notes](https://godotengine.org/releases/4.4/): Metal is Apple Silicon only.)
- The 15.8.2 RC bug hit Godot's **Project Manager**, which is the only part of Godot that defaults to OpenGL. `--rendering-driver metal` worked around it ([#124311](https://github.com/godotengine/godot/issues/124311)).
- If you choose Godot, use Forward+ or Mobile rather than Compatibility, and macOS OpenGL stops being a concern.

### 2. imgui-bundle's Metal escape hatch is broken in current releases
- imgui-bundle 1.92.900 removed `ImDrawData.cmd_lists_count`.
- wgpu 0.32.0 (2026-07-19), the latest release, still calls it ([v0.32.0 source](https://raw.githubusercontent.com/pygfx/wgpu-py/v0.32.0/wgpu/utils/imgui/imgui_backend.py)).
- The fix (#830, 2026-08-19) is only on main ([commits](https://github.com/pygfx/wgpu-py/commits/main)), and fastplotlib pins `imgui-bundle<1.92.900` because of this ([pyproject](https://raw.githubusercontent.com/fastplotlib/fastplotlib/main/pyproject.toml)).
- So with imgui-bundle 1.93.0 the stack is OpenGL-only on macOS until wgpu ships a new release.

### 3. Mac CPU architecture
- imgui-bundle 1.93.0 ships only `macosx_14_0_arm64` wheels, and dearpygui 2.3.1 only `macosx_13_0_arm64`.
- pygame-ce ships universal2 wheels, and raylib ships x86_64 and arm64 (PyPI JSON).
- Apple said macOS 26 Tahoe is the last release for Intel Macs ([MacRumors](https://www.macrumors.com/2025/06/09/intel-macs-no-more-updates/)), so an arm64-only build is fine for a new game.

### 4. Your machine (checked locally)
- **What you have:** macOS 15.8.1 (24H32), python.org Python **3.13.0**, uv **0.8.3**.
- **Python:** the current releases are 3.13.18, 3.14.10 and 3.15.2; 3.15.0 came out 2026-10-09 ([python.org/ftp](https://www.python.org/ftp/python/), [endoflife.date](https://endoflife.date/api/python.json)).

### 7. How fast the simulation can run

- So plan for a headless, fixed-tick simulation with numpy for bulk economy maths, and move hot loops to a compiled module (PyO3/maturin or Cython) only once profiling demands it.

## Fact-check: core_mechanics_gaps

**Overall:** Both FULL reports hold up well. Nearly every version and date in the core report matches PyPI, python.org, crates.io, GitHub and the runner images as of 2026-11-05. The exceptions are PyPy, which is now 8.0.1 with Python 3.12 beta, and ty, which moved to 0.0.98 today. The OpenTTD details in the mechanics report (town growth, payment formula, station rating, smooth economy, link-graph defaults, tick constants) match current master source almost line for line. An independent re-run of the micro-benchmarks on the same M3 Pro with CPython 3.13.0 landed within about 2x of both reports. So 'pure Python is fast enough at RT2 scale if routing is cached, periodic and kept off the per-tick path' stands.

Errors to fix:
- OpenTTD ticks are 27 ms, not 30.
- YAPF flushes its whole cache on any track change.
- concurrent.interpreters cannot run numpy.
- Artifact Signing is open to organizations in the EU, the UK and several other countries.
- Neither Briefcase nor PyInstaller can make an Intel or universal build, because imgui-bundle publishes only macOS 14+ arm64 wheels.
- Simutrans places city-triggered industries map-wide, not in the triggering city.
- TF2's extra building demands depend on a setting.
- OpenTTD's smooth economy applies only to primary industries.
- The claim about Nuitka's paid antivirus help has no source.

The real cross-report conflict is the interpreter. 3.14 is correct only for an imgui-bundle or pyglet frontend; Arcade 3.3.3's pymunk~=6.9.0 pin has no cp314 wheels. That pin, together with Arcade's age, makes Arcade a poor foundation, and Arcade 3.3.3 with Briefcase on 3.14 is a dealbreaker.

Recommended path:
- CPython 3.14 installed through uv, with the version pinned and locked.
- A headless, deterministic sim with integer economy maths.
- The imgui-bundle Hello ImGui runner with an ImPlot or draw-list map, and custom_background as the later hook for a custom renderer.
- PyInstaller builds for Apple Silicon (macOS 14+) and Windows x64, plus an easy Linux build.
- A 1-2 day spike that also covers audio, packaging the imgui-bundle assets, and a signed, notarized build.

Godot remains the fallback.

The largest risks no report covered are the lack of screen-reader support in Dear ImGui, the missing design for RT2-style train physics, and Windows code signing if the developer is an individual outside the US and Canada.

### Key findings

- For this game the hard frontend problem is panels and charts, not the map: none of pygame_gui, arcade.gui, pyglet.gui or raygui has a table/data-grid widget, while Dear ImGui (imgui-bundle 1.93.0) provides sortable, resizable tables, tooltips, docking and ImPlot time-series charts.

- Pyxel 3.0.0 (released 2026-11-05) is retro by design (16 colours, 256x256 image banks, no widgets) and is not a fit.

# Python-native 2D frameworks as the game frontend (checked 2026-11-05)

## Verdict
Use **Arcade 3.3.3 for the map and world layer, and Dear ImGui (imgui-bundle 1.93) for every panel and chart, both in the same pyglet window**. Run it on Python 3.13, and keep the simulation in a separate pure-Python package that never imports the frontend. For this game the map is the easier part and the panels are the hard part. None of the native toolkits (pygame_gui, arcade.gui, pyglet.gui, raygui) has a table widget. Only ImGui gives you sortable, resizable tables, tooltips, docking and time-series charts (through ImPlot).

## The 100k-tile map: Python's per-call cost is the limit
No framework can make 100k draw calls per frame from Python. raylib's own Bunnymark gets 10,500 sprites at 60 fps on CPython 3.12, against 180,000 in C ([README](https://github.com/electronstudio/raylib-python-cffi)). That leaves two options:
- keep the geometry on the GPU (Arcade or pyglet batches), or
- pre-render the terrain into chunk textures (pygame-ce, raylib).

## pygame-ce 2.5.8 + pygame_gui 0.6.14
- **Maintenance:** pygame-ce is the active fork. Version 2.5.8 came out 2026-08-09, with universal2 wheels for CPython 3.10–3.15 and Windows ARM64 support ([PyPI](https://pypi.org/project/pygame-ce/), [releases](https://github.com/pygame-community/pygame-ce/releases)). Releases come every 3–5 months. The SDL3 port is ongoing, with no date for 3.0. The original pygame has stopped at 2.6.1 (2024-09-29) ([PyPI](https://pypi.org/project/pygame/2.6.1/)).
- **Rendering:** drawing happens on the CPU. The GPU Renderer/Texture API in `pygame._sdl2.video` is documented as experimental and subject to change ([docs](https://pyga.me/docs/ref/sdl2_video.html)). Zooming means rescaling surfaces on the CPU, so you need fixed zoom steps with cached chunk surfaces, and a Retina screen has 4x the pixels to fill. Arcade's archived comparison says pygame slows down after a few thousand sprites ([archive](https://github.com/pythonarcade/arcade/blob/development/doc/_archive/pygame_comparison.rst)). There is no camera.
- **HiDPI:** on Retina it renders at half resolution by default, and [issue #1456](https://github.com/pygame-community/pygame-ce/issues/1456) is still open. `pygame.Window(allow_high_dpi=True)` only partly fixes it: you can't query the scale factor, and mouse coordinates are logical while drawing is in physical pixels. In a text-heavy game on your Mac, this shows.
- **macOS upside:** the normal path presents through SDL's renderer, which pygame-ce's docs say uses Metal on macOS. It does not depend on OpenGL.
- **UI:** pygame_gui has windows, scroll containers, selection lists, dropdowns, text entry, tooltips, tabs and JSON theming. It has no table or grid. Its last release was 2025-05-30 and its last commit 2025-06-15, so a single maintainer has been inactive for 17 months ([PyPI JSON](https://pypi.org/pypi/pygame_gui/json), [commits](https://github.com/MyreMylar/pygame_gui/commits/main)).
- **ImGui:** imgui-bundle's pygame backend needs a `DOUBLEBUF|OPENGL` display, where pygame's normal blitting no longer reaches the screen ([example](https://github.com/pthom/imgui_bundle/blob/main/bindings/imgui_bundle/python_backends/examples/example_python_backend_pygame.py)). You would end up writing an OpenGL renderer anyway.
- **Charts, packaging, community:** charts mean rendering matplotlib (Agg) to a surface or drawing lines by hand. Packaging works with PyInstaller, Nuitka and Briefcase (2.5.5 fixed Briefcase notarization). It has by far the most tutorials.
- **Verdict:** the easiest place to start. But zooming on the CPU, blurry Retina text and a stalled GUI with no tables make it the wrong long-term choice.

## Arcade 3.3.3 (stable) / 4.0.0.dev8
- **Maintenance:** the latest stable is 3.3.3 (2025-10-09). It pins pyglet~=2.1.5 and pymunk~=6.9.0 ([PyPI JSON](https://pypi.org/pypi/arcade/3.3.3/json)). pymunk 6.9.0 has no CPython 3.14 wheels ([PyPI](https://pypi.org/project/pymunk/6.9.0/)), so stay on 3.13. Eight 4.0 dev builds came out between Dec 2025 and 2026-10-05. They pin pyglet==3.0.dev11 and break some APIs (new default font, angle convention, stricter Sprite arguments) ([CHANGELOG](https://github.com/pythonarcade/arcade/blob/development/CHANGELOG.md)). The repo was last pushed 2026-10-30 and has about 2.1k stars. Its docs and examples are the best in this group.
- **Rendering:** OpenGL 3.3, with SpriteList data kept in GPU buffers. Arcade claims more than 1M stationary sprites at 60 fps (archive above). The layout I'd use:
  - terrain in one SpriteList, or a single tile shader;
  - track in a `ShapeElementList`, which draws static shapes in one call and is rebuilt only when track changes ([docs](https://github.com/pythonarcade/arcade/blob/development/doc/api_docs/api/drawing_batch.md));
  - a few hundred moving train sprites.
- **Camera, input and sim tick:**
  - `Camera2D` handles zoom, and `unproject()` converts screen positions to world positions for mouse picking ([docs](https://github.com/pythonarcade/arcade/blob/development/doc/api_docs/api/camera_2d.md)).
  - The mouse press, drag and release events cover dragging to lay track.
  - `on_fixed_update` with `fixed_rate` and `fixed_frame_cap` gives deterministic simulation ticks and fast-forward ([event loop](https://github.com/pythonarcade/arcade/blob/development/doc/programming_guide/event_loop.rst)).
- **UI:** arcade.gui has buttons, labels, text input, a read-only text area, dropdown, sliders, and box, grid and anchor layouts. The scroll area is experimental, and there are no tables or tooltips. The docs warn that changing label text often causes lag ([GUI concepts](https://api.arcade.academy/en/latest/programming_guide/gui/concepts.html)). 4.0.0.dev6 fixed a bug that dropped widget-heavy UIs to a few fps. Don't build ledger screens in it.
- **ImGui:** there is no official integration, and the old `arcade-imgui` (built on pyimgui) is inactive ([PyPI](https://pypi.org/project/arcade-imgui/)). `arcade.Window` is a subclass of pyglet's Window, so imgui-bundle's pyglet backend should attach to it. Its renderer saves and restores the shader program and vertex-array state. Not verified, so test it first.
- **HiDPI:** Retina works through pyglet. The fixes for text and drawing at 125–150% scaling on Windows exist only in unreleased code.
- **Packaging:** it ships a PyInstaller hook for Windows, Mac and Linux, and 3.3.3 fixed backend discovery inside bundles.

## pyglet 2.1.19 / 3.0.dev11
- **Maintenance:** very active. 2.1.19 came out 2026-10-11 and 3.0.dev11 on 2026-09-25 ([PyPI](https://pypi.org/project/pyglet/)). Version 3.0 rewrites the internals to support multiple backends, but the dev tree only contains gl, gl2 and webgl, with no Metal or Vulkan ([tree](https://github.com/pyglet/pyglet/tree/development/pyglet/graphics/api)). It also renames many APIs ([migration](https://pyglet.readthedocs.io/en/development/programming_guide/migration.html)).
- **Rendering and UI:** it has GPU batches and shapes, but no camera until 3.0. pyglet.gui is minimal: buttons, slider and text entry, with layouts added in 3.0 ([docs](https://pyglet.readthedocs.io/en/development/modules/gui.html)).
- **Best ImGui host:** imgui-bundle ships an official pyglet backend that requires pyglet 2 or newer and handles framebuffer scaling ([source](https://github.com/pthom/imgui_bundle/blob/main/bindings/imgui_bundle/python_backends/pyglet_backend.py)). Nobody has checked it against 3.0's renamed APIs.
- **HiDPI:** explicit `dpi_scaling` modes ([options](https://github.com/pyglet/pyglet/blob/master/doc/programming_guide/options.rst)).
- **Verdict:** the fallback host if the Arcade + ImGui combination causes trouble.

## raylib-python-cffi 6.2.0.0 (pyray + raygui)
- **Maintenance:** it follows upstream within about two weeks (raylib 6.2 on 2026-10-15, binding on 2026-10-26) ([PyPI](https://pypi.org/project/raylib/), [raylib](https://github.com/raysan5/raylib/releases)). It has essentially one maintainer and 251 stars, against 35.5k for raylib in C.
- **Rendering:** you issue draw calls every frame and raylib batches them internally, with Camera2D built in. The per-call cost from Python means pre-rendering terrain into RenderTexture chunks.
- **UI:** raygui is basic and redrawn every frame: list view, scroll panel, tab bar, dropdown, text box, spinner, message box. It has no table ([raygui](https://github.com/raysan5/raygui)). There's no maintained Python ImGui bridge; imraylib depends on the stale raylibpy and pyimgui ([PyPI](https://pypi.org/project/imraylib)).
- **Platform:** HiDPI is opt-in (reworked in 6.0). On macOS it uses GLFW and OpenGL 3.3. Nuitka is documented, and the docs are written for C.
- **Verdict:** the UI rules it out.

## Cross-cutting: OpenGL on macOS
Everything here except pygame-ce's normal path draws through Apple's deprecated OpenGL, which tops out at version 4.1 and runs on top of Metal.
- It still ships in macOS 26 and 27, but it breaks easily. In Oct 2026 a macOS 15.8.2 release candidate broke on-screen OpenGL on Apple Silicon: Godot, kitty and Alacritty showed blank windows until RC3 ([Apple forums](https://developer.apple.com/forums/thread/850550)).
- VisIt reports an OpenGL startup crash on macOS 27 ([issue](https://github.com/visit-dav/visit/issues/21223)).
- Rumours that it will be removed are unconfirmed ([thread](https://groups.google.com/g/js8call-improved/c/oOMaCrcsoGU)).

This doesn't rule anything out today. The protection is in the architecture: keep the simulation runnable without any window and independent of the frontend. That keeps a Metal-based path open later, such as [wgpu-py](https://pypi.org/project/wgpu/) 0.32 or [pygfx](https://pypi.org/project/pygfx/) 0.17 with imgui-bundle's wgpu backend. Kivy is also not worth it: its last release was 2.3.1 on 2024-12-26 ([PyPI](https://pypi.org/project/Kivy/)).

## Python GUI and tooling toolkits used as the shell of a UI-heavy simulation game (pygui)


### Key findings

- imgui-bundle is the best fit and very actively developed (1.93.0 on 2026-10-21, near-daily commits). Its immediate mode maps one-to-one onto a fixed-tick simulation, and Hello ImGui + ImPlot provide docking, sortable clipped tables and time-series charts in one wheel.
- The whole map can be an ImPlot plot fed from numpy: PlotImage for terrain, one Segments-flag PlotLine with per-segment colours for all track, PlotScatter for trains, and GetPlotMousePos for track laying. This avoids paying Python call overhead per primitive.
- imgui-bundle's Python runner always uses GLFW + OpenGL3, and Metal is reachable only through the pure-Python wgpu backend, so rendering code should sit behind a thin adapter.
- OpenGL is deprecated but still present on macOS 26 and 27 (the 27 release notes list no removal), with unconfirmed reports and rumours of removal. That is a medium-term risk for every OpenGL-based stack, not a current blocker.
- imgui-bundle has a bus factor of one and ships breaking API changes in point releases (1.92.800, 1.92.900, 1.93.0), so pin exact versions and upgrade deliberately.
- PySide6 6.12 on Qt 6.12 LTS (5-year support) is the most robust fallback and has the best tables, docking and undo. Its map is CPU-painted unless you use OpenGL, low-level QRhiWidget or the GPLv3/commercial-only Canvas Painter, and Qt 6 Python bindings carry noticeably higher per-call costs.
- For charts in a Qt build, use pyqtgraph (MIT). Qt Charts has been deprecated since 6.10 and Qt Graphs is GPLv3/commercial only, while PySide6 itself is LGPLv3.
- Dear PyGui is officially in maintenance mode with one active volunteer maintainer and only experimental docking that cannot be set up in code, so it is unsuitable as the base of a multi-year project.
- Kivy (no release since 2024-12-26) and Textual (terminal character grid; its company closed in 2025) are a poor fit and a dealbreaker respectively for this game's map and panels.
- Browser stacks (NiceGUI 4.0.0, pywebview, Flet) excel at dashboards but force the animated map into JavaScript and send every update over a websocket or bridge.
- Running imgui-bundle's UI over pyglet, Arcade or pygame-ce is possible via pure-Python backends but fragile: no DPI handling, pygame must run in OpenGL mode, and pyglet 3 is renaming modules. Host everything in Hello ImGui and add moderngl only if needed.
- De-risk with a 1-2 day spike on the Mac and a Windows laptop with integrated graphics: 50k track segments, 500 interpolated trains, a 5k-row sortable table and four docked panels at 60 fps, plus a PyInstaller .app/.exe build.

### Full report

# Python UI shells for a mechanics-first railroad tycoon (checked 2026-11-05)

**Pick: Dear ImGui Bundle (`imgui-bundle`, using the Hello ImGui runner and ImPlot), pinned to an exact version, with the map drawn inside an ImPlot plot from numpy arrays.** Fallback: PySide6 6.12 LTS + pyqtgraph. Do not build on Dear PyGui, Kivy, Textual or a browser stack.

## 1. imgui-bundle (recommended)

**Health.**
- 1.93.0 shipped 2026-10-21 with Dear ImGui 1.93. It is the sixth PyPI release of 2026 ([PyPI](https://pypi.org/project/imgui-bundle/#history)).
- The owner wrote 16 of the 20 commits between Oct 23 and Nov 5 ([commits](https://github.com/pthom/imgui_bundle/commits/main)).
- **Bus factor is 1.** The README names one maintainer and about 20 contributors ([repo](https://github.com/pthom/imgui_bundle)).
- Mitigations:
  - The bindings are generated by litgen into nanobind ([dev docs](https://github.com/pthom/imgui_bundle/blob/main/docs/book/devel_docs/intro.md)), so updates are largely mechanical.
  - Upstream [Dear ImGui](https://github.com/ocornut/imgui/releases) is very healthy.
  - [ImPlot](https://github.com/epezent/implot/releases) has a new maintainer and has reached v1.x.
- **API churn is real.**
  - 1.92.800 swapped the `thickness`/`flags` arguments of `add_rect`/`add_polyline`.
  - 1.92.900 changed how slider/drag edits are committed.
  - 1.93 removed some APIs ([releases](https://github.com/pthom/imgui_bundle/releases)).
  - fastplotlib pins `imgui-bundle<1.92.900` because a removed attribute broke wgpu's renderer ([pyproject](https://github.com/fastplotlib/fastplotlib/blob/main/pyproject.toml)).

**Map.** Use ImPlot as the canvas ([implot.h](https://github.com/epezent/implot/blob/master/implot.h)):
- `ImPlotFlags_Equal` with hidden axes gives pan and zoom for free.
- Terrain is a numpy RGBA array, uploaded once as a texture and drawn with `PlotImage`.
- The whole track network is a single `PlotLine` call with `ImPlotLineFlags_Segments`, with per-segment colours from `ImPlotSpec.LineColors`.
- Stations and trains are drawn with `PlotScatter` using size and colour arrays.
- Custom glyphs use `GetPlotDrawList()`/`PlotToPixels()`.
- `GetPlotMousePos()` returns the mouse position in world coordinates.
- The input map can be remapped, so left-click lays track while another button pans.

If this runs out, draw with OpenGL in Hello ImGui's `custom_background` callback or into a texture ([demo](https://github.com/pthom/imgui_bundle/blob/main/bindings/imgui_bundle/demos_python/demos_immapp/demo_custom_background.py)).

**Binding overhead.**
- nanobind is about 3× faster than pybind11 on simple calls and about 10× faster when objects are passed ([nanobind](https://nanobind.readthedocs.io/en/latest/benchmark.html)).
- The project's docs claim Python overhead is "< 0.5ms per frame typically" ([docs](https://github.com/pthom/imgui_bundle/blob/main/docs/book/intro/key_features.md)).
- My planning figure, which I have not measured, is about 0.2–1 µs per call.
- Thousands of widget/draw calls per frame are fine. 50k separate `add_line` calls are not, so batch through numpy and ImPlot.

**Panels.**
- Tables support multi-column sort specs and a list clipper, which handles 10k-row cargo tables.
- ImPlot covers the time-series charts.
- Hello ImGui docking is defined in code, supports several layouts and saves settings between sessions ([docs](https://github.com/pthom/imgui_bundle/blob/main/docs/book/core_libs/hello_imgui_immapp.md)).
- Also included: modal popups, file dialogs, a node editor, and ImGui Test Engine for scripted UI tests (it has its own licence).

**Loop.** Immediate mode is the natural partner for a fixed-tick simulation:
- Each frame, run 0..N ticks from an accumulator: none when paused, more on fast-forward, with a cap.
- Interpolate train positions, then redraw everything from the current state.
- There are no observers and no stale widgets. A track-laying preview is just drawing the ghost track this frame.
- Turn idling off with `fps_idling.enable_idling = False`. By default the app drops to 10 fps when there is no input.

**Platform and packaging.**
- Wheels exist for macOS 14+ arm64 and Windows x64/ARM64, on CPython 3.11–3.15.
- **The Python build always uses GLFW + OpenGL3.** The Metal and Direct3D backends are C++ only ([build guide](https://github.com/pthom/imgui_bundle/blob/main/docs/book/devel_docs/build_guide.md)).
- The escape hatch is the pure-Python wgpu backend (`wgpu.utils.imgui.ImguiRenderer`), which uses Metal on macOS ([example](https://github.com/pthom/imgui_bundle/blob/main/bindings/imgui_bundle/python_backends/examples/example_python_backend_wgpu.py)).
- PyInstaller recipes (a Windows .exe, and a macOS `.app` via `BUNDLE`) and Nuitka recipes are documented ([deploy](https://github.com/pthom/imgui_bundle/blob/main/docs/book/python/desktop_deploy.md)).
- PyInstaller 6.22.3 supports Python 3.8–3.15, arm64 and code signing ([PyPI](https://pypi.org/project/pyinstaller/)).

**Precedent.**
- I found no shipped Python game built on it.
- Dear ImGui is listed for genre titles such as Railway Empire 2, Victoria 3 and Planet Zoo, mostly for internal tools ([wiki](https://github.com/ocornut/imgui/wiki/Software-using-dear-imgui)).
- Pioneer Space Sim runs its whole player-facing UI on ImGui, trade screens included, driven from Lua. It removed its old UI in 2022 ([GamingOnLinux](https://www.gamingonlinux.com/2022/02/free-and-open-source-space-sim-pioneer-gets-a-big-ui-upgrade/)).

## Shared risk: OpenGL on macOS
- Apple deprecated OpenGL in 2018.
- The macOS 26 notes remove AGL but keep OpenGL ([notes](https://developer.apple.com/documentation/macos-release-notes/macos-26-release-notes)).
- The macOS 27 notes do not mention removing OpenGL ([notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes)).
- However, one developer reports an OpenGL-linked Qt 6.9 build failing on a macOS 27 beta, and repeats a rumour that OpenGL will be removed in a point release ([thread](https://groups.google.com/g/js8call-improved/c/oOMaCrcsoGU)).
- This is not a blocker today. Keep rendering behind a thin adapter so it can be swapped.

## 2. PySide6 + pyqtgraph (robust fallback)
**Health.** PySide6 6.12.0 (2026-10-08) runs on Qt 6.12 LTS, which gets 5 years of maintenance ([Qt](https://www.qt.io/blog/qt-6.12-released), [PyPI](https://pypi.org/project/PySide6/#history)). The Qt Company backs it. pyqtgraph 0.14.0 (2025-11-16) has a small team committing as recently as 2026-11-05 ([commits](https://github.com/pyqtgraph/pyqtgraph/commits/master)).

**Map.**
- QGraphicsView handles "millions of items" in mostly static scenes, and `NoIndex` mode suits animated items. It provides hit-testing, hover, z-order and level-of-detail, and QUndoStack can handle undo for track edits ([docs](https://doc.qt.io/qt-6/graphicsview.html)).
- The pyqtgraph alternative is ViewBox + ImageItem + `PlotCurveItem(connect='pairs')` + ScatterPlotItem.
- Painting is CPU QPainter unless you choose one of these GPU options:
  - OpenGL via `QOpenGLWidget`, which carries the same macOS risk.
  - The low-level `QRhiWidget` (Metal/D3D11, needs precompiled shaders) ([docs](https://doc.qt.io/qtforpython-6/PySide6/QtWidgets/QRhiWidget.html)).
  - Canvas Painter, which is available only under GPLv3 or a commercial licence.

**Overhead.**
- Qt 6 bindings make each Python call more expensive.
- In one load test, PythonQwt measured about 2.9 s on PySide6, 2.3 s on PyQt6 and 1.9 s on PyQt5. It also timed PyQt6 enum-flag operations at about 6 µs each ([PythonQwt](https://github.com/PlotPyStack/PythonQwt/blob/master/doc/issue93_optimization_summary.md)).
- Do not override `paint()` on each item. Paint all trains in one item.

**Panels.**
- These are the best of any option: QTableView with proxy models, QDockWidget or PySide6-QtAds (5.1.1.1, built for 6.12.0) ([PyPI](https://pypi.org/project/PySide6-QtAds/)), and native dialogs.
- Use pyqtgraph for charts. Qt Charts has been deprecated since 6.10, and Qt Graphs is GPLv3 or commercial only ([docs](https://doc.qt.io/qt-6/qtgraphs-index.html)). PySide6 itself is LGPLv3.

**Loop.** Qt is retained mode. A QTimer drives the ticks, the map repaints at 60 Hz, and the panels poll state at 4–10 Hz.

**Packaging.** Options are PyInstaller's hooks, `pyside6-deploy` (Nuitka-based, standalone by default since 6.12) ([docs](https://doc.qt.io/qtforpython-6/deployment/deployment-pyside6-deploy.html)), and Briefcase's PySide6 bootstrap ([docs](https://briefcase.beeware.org/en/stable/reference/commands/new.html)). Bundles are larger than with imgui-bundle.

## 3. Dear PyGui (avoid)
- The latest release is 2.3.1 (2026-05-01) ([PyPI](https://pypi.org/project/dearpygui/#history)).
- The project is officially in maintenance mode ([wiki](https://github.com/hoffstadt/DearPyGui/wiki/What's-going-on%3F)), and v-ein wrote 18 of the last 20 commits ([commits](https://github.com/hoffstadt/DearPyGui/commits/master)).
- It lags upstream: 2.3 bundles ImGui 1.92.5 and ImPlot 0.17 ([releases](https://github.com/hoffstadt/DearPyGui/releases)).
- In its favour, it renders with Metal on macOS and DirectX 11 on Windows ([README](https://github.com/hoffstadt/DearPyGui)).
- Against it:
  - It is a retained-mode wrapper over ImGui.
  - Docking is "experimental because you cannot programmatically set up the docking positions" ([docs](https://dearpygui.readthedocs.io/en/latest/extra/video-tutorials.html)).
  - Its showcase games are Tetris and Snake demos.

## 4. Kivy (poor fit)
2.3.1 (2024-12-26) is still the latest release ([PyPI](https://pypi.org/project/Kivy/#history)), though the master branch is busy with SDL3 work ([commits](https://github.com/kivy/kivy/commits/master)). Its widgets are designed for touch, and it has no data grid, no docking and no maintained charts.

## 5. Textual (dealbreaker)
The latest release is 8.2.8 (2026-06-30). Textualize, the company behind it, closed in 2025, and Will McGugan now maintains it ([blog](https://textual.textualize.io/blog/2025/05/07/the-future-of-textualize/)). There have been two commits since July ([commits](https://github.com/Textualize/textual/commits/main)). A terminal's character grid cannot show a zoomable map with smooth trains.

## 6. Browser-based
- NiceGUI 4.0.0 (2026-11-04) is active and excellent for dashboards. It offers AG Grid, ECharts, the new `ui.uplot`, a native window via pywebview, and PyInstaller packaging ([releases](https://github.com/zauberzeug/nicegui/releases), [deploy](https://nicegui.io/documentation/section_configuration_deployment)).
- But every update crosses a websocket, and a smooth map would have to be written in JavaScript.
- pywebview 6.2.1 with your own web frontend has the same two-language cost.
- Flet 1.1.0 ([releases](https://github.com/flet-dev/flet/releases)) drives a Flutter canvas from Python over a protocol, which does not suit 60 fps map updates.
- Slint's Python binding is still beta ([PyPI](https://pypi.org/project/slint/)).

## 7. ImGui over pyglet, Arcade or pygame-ce
This combination is possible but fragile:
- The pure-Python backends have "no DPI handling, themes or assets" ([docs](https://github.com/pthom/imgui_bundle/blob/main/docs/book/python/pure_python_backend.md)).
- pygame must run in `OPENGL` mode, so its normal 2D blitting is lost ([example](https://github.com/pthom/imgui_bundle/blob/main/bindings/imgui_bundle/python_backends/examples/example_python_backend_pygame.py)).
- Arcade 3.3.3 pins pyglet ~=2.1.5 ([PyPI](https://pypi.org/project/arcade/)), while its development branch is moving to pyglet 3.0.dev, which renames the GL modules ([PR](https://github.com/pythonarcade/arcade/pull/2842)).
- moderngl-window has an imgui_bundle integration but has not released since January 2025 ([PyPI](https://pypi.org/project/moderngl-window/)).

Host everything in Hello ImGui instead. Only if ImPlot is not enough, add moderngl (5.13.0, October 2026) into Hello ImGui's GL context.

## Recommendation
Pick **imgui-bundle**. It fits your priorities:
- Dozens of data panels, charts and docking come in one MIT-licensed wheel.
- Immediate mode removes the code that keeps widgets in sync with the simulation, which dominates retained-mode tycoon UIs.
- ImPlot gives you a numpy-fed, zoomable map on day one.

Guardrails:
- Pin the exact version.
- Keep the simulation in a package with no UI imports, so moving to Qt later stays possible.
- Put all drawing behind a `MapRenderer` interface, so GLFW/OpenGL can be swapped for wgpu/Metal.

Choose Qt instead only if a native look and a 5-year LTS matter more to you than development speed.

Before committing, run a 1–2 day spike on your Mac and on a Windows laptop with integrated graphics. It should reach 60 fps with 50k track segments, 500 interpolated trains, a 5k-row sortable table and four docked panels, and include a PyInstaller .app/.exe build.

Also note that your python.org build is 3.13.0, the first 3.13 release. Update to the latest 3.13.x patch.


## Full game engines, and hybrid designs that keep a Python simulation (engines)


### Key findings

- Godot 4.7.2 (stable since 18 Aug 2026) with statically typed GDScript is the best fit: MIT-licensed, syntax similar to Python, a Control-node UI system strong enough for Godot's own editor, universal macOS export and maintained test frameworks (GUT 9.7, gdUnit4 6.2.3).
- Typed GDScript runs at roughly CPython speed (a Godot PR micro-benchmark on M1: 6.0–8.9 ms vs 9.1 ms for CPython 3.10), so moving the sim from Python costs no speed; C#/GDExtension stay available for hot loops profiling identifies.
- There is no production-ready way to run Python inside an engine: py4godot is alpha, marked unstable, macOS arm64-only; godot-python never shipped a Godot 4 release; Unity's Python works only in the Editor and its support ended at 6.1.
- A Python sim process with a Godot client over JSON pipes or WebSocket is technically easy and latency is negligible locally, but it roughly doubles the work (protocol, process lifecycle, number-to-float conversion in Godot's JSON, two debuggers, two runtimes to sign and notarize), so defer it.
- Write the GDScript sim as node-free classes on a fixed tick, with command objects in and events out; that allows background threads, headless tests and a later split into a separate process.
- Godot's main UI gap for tycoon tables is that Tree has multi-column headers but no built-in sorting (a small DIY job); Unity's MultiColumnListView sorts out of the box, but that alone doesn't justify Unity.
- Unity 6 is capable but brings closed-source licensing risk (Pro $2,310/seat/yr above $200k revenue plus funding) and a Mono-to-CoreCLR/.NET 10 migration (6.7 LTS is the last Mono release) during the project's lifetime.
- Bevy (0.20.1) has breaking changes every 3–5 months and no editor; together with learning Rust and ECS, that's a dealbreaker for a first game.
- Defold (HUD-oriented GUI) and LÖVE (no UI system; last stable release Dec 2023) are poor fits for a panel-heavy tycoon game.
- Budget US$99/yr for an Apple Developer ID to notarize Mac builds with any engine, and use Rider (free for non-commercial use) or VS Code for GDScript rather than PyCharm.

### Full report

## Bottom line
**My pick: Godot 4.7.x with statically typed GDScript. Move to 4.8 once it is stable.** Write the simulation as plain GDScript classes that don't depend on scene nodes, advanced by a fixed-tick clock. Player actions go in as command objects, and the sim sends events out to a UI built from Control nodes. Don't embed Python. Keep "Python sim as a separate process" as an option for later. Use Python only for an optional, time-boxed prototype of the economy.

## Godot 4.x with GDScript (recommended)
- **Version and maintenance:** 4.7 stable shipped on 18 Jun 2026. The current stable release is **4.7.2 (18 Aug 2026)**. 4.8 is feature-frozen at beta 2 (29 Oct 2026) and has no stable date yet ([archive](https://godotengine.org/download/archive/), [4.8 beta 2](https://godotengine.org/article/dev-snapshot-godot-4-8-beta-2/)). A feature release lands about every 5–6 months.
- **License and business risk:** The engine is MIT-licensed and run by the non-profit Godot Foundation. Its commercial partner W4 Games raised an $18M Series B in 2026, but the license stays with the Foundation, so W4 can't change it ([W4](https://w4games.com/blog/w4-games-news-1/w4-games-raises-18-million-to-accelerate-international-presence-193)). This is the lowest business risk of any option here.
- **Learning curve for a Python developer:** The official reference calls the syntax "similar to Python" but says GDScript is not Python. For example, with two ints, `5 / 2 == 2` ([GDScript reference](https://docs.godotengine.org/en/stable/tutorials/scripting/gdscript/gdscript_basics.html)). Static typing is now solid: typed arrays, typed dictionaries (4.4), and abstract classes plus variadic functions (4.5) ([4.4](https://godotengine.org/releases/4.4/), [4.5](https://godotengine.org/releases/4.5/)). The built-in editor includes a debugger, a profiler and live reload.
- **IDE:** **PyCharm is not a documented GDScript IDE.** JetBrains bundles its GDScript plugin in Rider, which is free for non-commercial use, and documents it only there ([godot-support](https://github.com/JetBrains/godot-support)). VS Code also works.
- **Unit testing:** Two maintained frameworks exist:
  - **GUT 9.7.x** adds Godot 4.7 compatibility (Jun/Jul 2026) ([releases](https://github.com/bitwes/Gut/releases)).
  - **gdUnit4 6.2.3** (1 Nov 2026) supports GDScript and C#, has a headless CLI runner and writes JUnit XML ([repo](https://github.com/MikeSchulze/gdUnit4)).
- **2D map:**
  - Terrain: `TileMapLayer` (the old TileMap node is deprecated), which batches tiles in quadrants ([docs](https://docs.godotengine.org/en/stable/classes/class_tilemaplayer.html)).
  - Track: `_draw()` or Line2D polylines.
  - Trains: PathFollow2D or MultiMesh.
  - Camera: Camera2D handles zoom and pan.
  - Routing: native **AStar2D** works over a weighted track graph and lets you disable nodes ([AStar2D](https://docs.godotengine.org/en/stable/classes/class_astar2d.html)).
  - Overlays: 4.7 adds DrawableTexture2D for things like demand heat-maps ([4.7](https://godotengine.org/releases/4.7/)).
- **UI, the deciding factor:** Godot builds UIs from Control nodes, containers and Theme resources. Godot's own editor is built the same way. Recent additions that help a tycoon UI:
  - FoldableContainer (4.5).
  - Control offset transforms and searchable PopupMenus (4.7).
  - Auto-fit Labels and sticky Tree rows (4.8 beta).
  - One gap: `Tree` supports multiple columns and a `column_title_clicked` signal, but has **no built-in sorting**. You sort your model and rebuild the rows, which is a small job ([Tree](https://docs.godotengine.org/en/stable/classes/class_tree.html)).
- **Charts:** Nothing is built in. Options:
  - TauPlot: BSD-3, pure GDScript, Godot 4.5+, v0.2.1 from Oct 2026, marked unstable by its author. Supports line, bar, scatter and area charts, plus streaming data ([store](https://store.godotengine.org/asset/ze2j/tau-plot/)).
  - Easy Charts: active, last pushed Oct 2026 ([repo](https://github.com/fenix-hub/godot-engine.easy-charts)).
  - Hand-rolled: a finance line chart drawn with `draw_polyline` is about a weekend's work. That's what I'd do.
- **Export to macOS and Windows:**
  - The official templates build **universal (arm64 + x86_64) macOS apps**.
  - Signing works through Xcode codesign, rcodesign, or Godot's built-in ad-hoc signature.
  - Notarization needs a Developer ID certificate ([macOS export](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_macos.html)), which comes with the US$99/yr Apple Developer Program ([Apple](https://developer.apple.com/support/compare-memberships/)).
  - 4.8 switches the default download to separate per-architecture builds but still offers universal ones ([4.8 beta 1](https://godotengine.org/article/dev-snapshot-godot-4-8-beta-1/)).
  - Windows export is simple.
- **Simulation performance:**
  - In a micro-benchmark posted on Godot PR #70838, typed GDScript took 6.0–8.9 ms on an M1 against 9.1 ms for CPython 3.10. A run on an i7 favored Python ([PR #70838](https://github.com/godotengine/godot/pull/70838)). Plan for roughly CPython-class speed.
  - Native helpers (AStar2D, packed arrays, sorting) do heavy work in C++.
  - WorkerThreadPool can run the sim off the main thread. That only works if the sim doesn't touch scene nodes, since the scene tree isn't thread-safe.
  - Per frame, only move trains. Run the economy at day-level ticks.
  - If you later need very fast fast-forward, move the hot loops that profiling shows to C# or GDExtension (godot-rust 0.5.5, Aug 2026, [crates](https://crates.io/crates/godot)).
- **Data-driven content and modding:**
  - Content: define cargo, industry and building types as custom `Resource` classes (`.tres` files you can edit in the inspector), or as JSON/CSV.
  - Mods: mods load as PCK/ZIP packs via `ProjectSettings.load_resource_pack()` ([docs](https://docs.godotengine.org/en/stable/tutorials/export/exporting_pcks.html)). Mod scripts are not sandboxed.

## Godot 4.x with C#
- **Setup:** C# needs the separate ".NET" editor build. Godot 4.5–4.7 use .NET 8, and **4.8 requires .NET 10**.
- **Export:** Desktop export works, including universal macOS ([4.7 downloads](https://godotengine.org/download/archive/4.7-stable)). Web export doesn't, which doesn't matter for this project ([C# basics](https://docs.godotengine.org/en/stable/tutorials/scripting/c_sharp/c_sharp_basics.html)).
- **Pros:** real static types, faster tight loops, NuGet packages, and tests through gdUnit4Net.
- **Cons:** a second toolchain, fewer tutorials, conversion overhead on every call into the engine, and the .NET 10 bump coming with 4.8.
- **No need to decide now:** the .NET build opens GDScript projects, so you can add C# for the sim core later.

## Python inside Godot: a dealbreaker today
- **py4godot**, the only active project:
  - Latest version is 4.7-alpha21 (6 Aug 2026), which its author has marked unstable.
  - It supports Windows x64, Linux x64 and **macOS arm64 only**. With no Intel Mac support, you can't ship a universal Mac build ([store](https://store.godotengine.org/asset/niklas-zimmer/py4godot/)).
  - Its README says: "Consider this more as a demo and don't use this for bigger projects" ([repo](https://github.com/niklas2902/py4godot)).
- **godot-python:** the Godot 4 rewrite lives on the `godot4-meson` branch. Its last commit was on 25 Feb 2026, and there is still no Godot 4 release more than 3.5 years after Godot 4.0 came out ([repo](https://github.com/touilleMan/godot-python)).
- **godot-python-extension:** experimental and relies on the system-installed Python ([repo](https://github.com/maiself/godot-python-extension)).

## Unity 6
- **Versions:**
  - 6.3 LTS, released Dec 2025, is supported until Dec 2027.
  - 6.6 (Sep 2026) is the newest update release.
  - 6.7 LTS is in beta and due in late 2026 ([overview](https://unity.com/releases/release-overview)).
- **Runtime transition ahead:** Unity calls 6.7 the "last Unity release built upon Mono". 6.8 moves to CoreCLR with .NET 10 and C# 14 ([status](https://discussions.unity.com/t/coreclr-scripting-and-ecs-status-update-march-2026/1711852)). A multi-year project would live through that migration.
- **License:**
  - Personal is free for up to $200k of revenue plus funding, and the splash screen is optional.
  - Pro costs $2,310 per seat per year from 12 Jan 2026.
  - The Runtime Fee was cancelled in Sep 2024 ([pricing](https://unity.com/products/pricing-updates)).
  - The engine is closed source, and Unity has a 2023 history of damaging developer trust over pricing.
- **Strengths:**
  - The best sortable tables of any option: UI Toolkit's `MultiColumnListView` sorts by column out of the box ([API](https://docs.unity.com/en-us/engine/6000.3/script-reference/unityengine/uielements/multicolumnlistview)).
  - Runtime data binding.
  - XCharts for charts (MIT, active) ([repo](https://github.com/XCharts-Team/XCharts)).
  - A mature 2D Tilemap and NUnit-based tests.
- **Weaknesses:**
  - Unity's own docs still recommend the older uGUI system for in-game UI ([compare](https://docs.unity3d.com/6000.4/Documentation/Manual/UI-system-compare.html)), so you end up learning two UI systems.
  - The editor is heavier than Godot's.
  - Its Python Scripting package works only in the Editor, and its support ended at 6.1 ([known issues](https://docs.unity3d.com/Packages/com.unity.scripting.python@7.0/manual/known-issues.html)).
- **Verdict:** capable, but no real advantage over Godot for a 2D game built around panels.

## Bevy (Rust)
- **Releases:** 0.20 shipped on 8 Oct 2026 (0.20.1 on 28 Oct), after 0.17 in Sep 2025, 0.18 in Jan 2026 and 0.19 in Jun 2026 ([news](https://bevy.org/news/)). The project says "each release has its fair share of breaking changes" ([migration](https://bevy.org/learn/migration-guides/introduction/)).

- **Practical stack:** bevy_egui 0.43 (Bevy 0.20, egui 0.36) with egui_plot for panels and charts, and bevy_ecs_tilemap 0.20 for tiles.
- **Strength:** the best raw simulation performance of any option.
- **Verdict:** a **dealbreaker for this project.** You would be learning Rust, ECS and game development all at once, on an engine that keeps breaking its API.

## Defold and LÖVE
- **Defold 1.14.0** (12 Oct 2026, [releases](https://github.com/defold/defold/releases)): free with a source-available license, scripted in Lua. Its GUI system is built for game HUDs. The Druid library adds scroll views, grids and data lists ([Druid](https://github.com/Insality/druid)), but there are no tables, trees or charts. Poor fit.
- **LÖVE:** the latest stable release is still **11.5 from Dec 2023**. 12.0 hasn't shipped, even though commits are still landing in Nov 2026 ([releases](https://github.com/love2d/love/releases)). It's a framework with no UI system and no editor.

## Hybrids
**(a) Python simulation as a separate process, with a Godot frontend**
- **Feasible:** Godot can start the sim with `OS.create_process` or `execute_with_pipe` (stdio pipes), or connect to it over WebSocketPeer or StreamPeerTCP ([OS](https://docs.godotengine.org/en/stable/classes/class_os.html)).
- **Encoding:** use JSON. Godot's JSON parser is native code. Msgpack and protobuf exist only as GDScript add-ons (for example [godobuf](https://github.com/oniksan/godobuf)), so I'd expect them to be slower.
- **Snapshots vs deltas:**
  - Send the static world once, with large grids as binary frames.
  - Each tick, send a full snapshot of the dynamic state that is on screen. My estimate is a few hundred trains at 10–20 Hz, a trivial load on a local connection.
  - Send player commands with request IDs.
  - Interpolate train movement on the client.
  - Add deltas later only if needed.
- **Gotchas:**
  - Godot's JSON parser turns every number into a float, including IDs ([JSON](https://docs.godotengine.org/en/stable/classes/class_json.html)).
  - Processes Godot starts keep running after Godot exits, unless you kill them or the sim exits when its pipe closes.
  - Every UI action becomes a remote call. Track-laying previews need either a round trip or a copy of the cost rules on the client.
  - You debug with two debuggers.
- **Packaging two runtimes:**
  - Bundle a Python runtime with [python-build-standalone](https://github.com/astral-sh/python-build-standalone/releases) or PyInstaller.
  - On macOS, sign every native binary with the hardened runtime before notarizing ([example](https://haim.dev/posts/2020-08-08-python-macos-app)).
  - On Windows, expect antivirus false positives on PyInstaller builds ([#5854](https://github.com/pyinstaller/pyinstaller/issues/5854)).
- **Verdict:** latency isn't the problem; the amount of extra work is. **Keep it as a later option.** If the GDScript sim is built around commands and events from the start, it can be split out later.

**(b) Embedding Python inside the engine:** no. Godot's bindings aren't usable (see above), Unity's Python runs only in the Editor, and Bevy would need a do-it-yourself PyO3 setup.

**(c) Prototype in Python, then port:** worth doing only as a 2–4 week "economy lab" with no graphics. Model cities, industries, demand and growth rules with pytest and matplotlib to check that the main mechanic is fun. Then port the rules to GDScript, which is mostly mechanical given the similar syntax, and stop maintaining the prototype.

## Simulation-core architecture, Python performance, testing/balancing, and packaging (core)


### Key findings

- Python is fast enough for a Railroad Tycoon 2-scale sim. On this M3 Pro, CPython 3.13.0 measured about 265 ns per realistic train update, 170 ns per industry production step and 4.2 ms for a full Dijkstra over 10k nodes, so the real risks are per-tick pathfinding and cargo routing, not entity counts.
- Build a headless, deterministic sim package: fixed ticks, systems updating at different rates and spread across ticks (OpenTTD: 30 ms ticks, 74 ticks/day, each tile every 256 ticks), commands as the only way to change state, events out, and a budget of 2 ms or less per tick so fast-forward stays smooth.
- Determinism needs integer or fixed-point money, cargo and positions, plus your own RNG wrapper over Random.random(). Python only promises random()'s sequence across versions, and numpy's Generator only on the same build and machine.
- ECS libraries (esper 3.9, tcod-ecs 5.5.2) are maintained but a poor fit. Use slots dataclasses in registries keyed by integer ID, systems as plain functions, and numpy arrays for bulk data and monthly statistics.
- Saves: msgspec MessagePack compressed with stdlib compression.zstd (3.14), with a format version and a chain of migration functions. Pickle is a dealbreaker: loading can run arbitrary code, and refactors break old saves.
- Moddable content: TOML checked by pydantic and compiled into tables indexed by integer ID, with a JSON Schema for modders and declarative rules (no eval) for city and building evolution.
- Graphs: hand-written A* over a condensed, direction-aware segment graph with cached segment costs; rustworkx 0.18.1 for station-graph and all-pairs work; networkx 3.7 only as a test oracle; igraph is a poor fit for a network the player edits constantly.
- Cargo with destinations (OpenTTD cargodist style) is the most expensive mechanic. Keep it cheap: route between stations only, cap demand to the top-N destinations, store per-station next-hop tables, and recompute in the background or spread over ticks, applying results at fixed ticks.
- Develop on CPython 3.14.10 with the normal GIL build. 3.13 now gets security fixes only, 3.15 is four weeks old and Nuitka does not support it yet, and free-threading is blocked because pygame-ce publishes no free-threaded wheels.
- Speed-up order: algorithms first, then numpy, rustworkx, mypyc or Cython, numba, and Rust via PyO3/maturin last. Keep numba out of the shipped game unless needed: about 40 MB of llvmlite, a compile pause on first call, and a deprecated ahead-of-time compiler.
- Testing core: hypothesis stateful tests over random player-command sequences with money and cargo conservation invariants, determinism and save-round-trip hash checks, syrupy golden runs, and hash comparison between macOS and Windows in CI.
- Balancing: headless runs over many seeds in a process pool, written to Parquet and analysed with polars and matplotlib in Jupyter. City growth from deliveries feeds on itself, so design for growth that levels off (S-curve) and test that growth rates stay bounded.
- Packaging: PyInstaller 6.22.3 in folder mode, Apple Silicon-only on macOS plus x64 Windows, built on each OS in CI. Use Briefcase 0.4.7 instead if you want signing, notarization and installers automated.
- Distribution costs: Steam requires Apple notarization for new macOS apps, so the Apple Developer Program is mandatory. Microsoft's Artifact Signing ($9.99/month) is open to individuals only in the US and Canada; elsewhere you need a commercial certificate. Unsigned PyInstaller builds risk antivirus false alarms.
- Python games already ship commercially on Steam: Ren'Py has 8,000+ works including Doki Doki Literature Club and Slay the Princess, and Yawnoc (pygame + ModernGL) is on Steam.
- Tooling: upgrade uv from 0.8.3 to 0.13.7; use ruff 0.17.3, mypy 2.4.1 in strict mode (keeps mypyc available), prek for pre-commit checks, and GitHub Actions on macOS 26 and Windows with setup-uv v10.

# Sim core, performance, testing and packaging (checked 2026-11-05)

**Bottom line:** Python works for this game if the simulation is built around Python's limits:
- a headless, deterministic sim
- integer money and cargo amounts
- staggered updates
- condensed track graphs
- cargo routing as a background job

Recommended stack:

| Area | Choice |
|---|---|
| Runtime | CPython 3.14, standard GIL build |
| Data model | Plain dataclasses plus numpy |
| Saves | msgspec |
| Content files | TOML checked by pydantic |
| Pathfinding | Hand-written A*, plus rustworkx |
| Tests | pytest, hypothesis, syrupy |
| Balancing | polars in Jupyter |
| Packaging | PyInstaller, or Briefcase |

## 1. Simulation architecture

**Headless `sim` package.** It must not import any UI code; CI checks this. The game, the tests and the batch balancer all drive it through the same small API:
- `submit(command)`
- `step()`
- read-only state
- a list of events per tick (e.g. `CargoDelivered`, `BuildingUpgraded`)

**Fixed timestep, with systems updating at different rates.**
- OpenTTD's precedent: 30 ms ticks, 74 ticks per in-game day ([date.h](https://code.theleruby.com/cpp/openttd-patchpack/source/files/071700f4fb71de05c639e810b61241acedbb26f8/date.h)), and each tile updated once every 256 ticks ([changeset](https://code.theleruby.com/cpp/openttd-patchpack/source/changeset/5550f5cdc59de529e5ed33a99f99bac4bc276eff)).
- Copy the idea: trains move every tick, industries update daily (spread across ticks by ID), cities update monthly.
- The renderer interpolates between ticks, and the loop caps ticks per frame ([Fix Your Timestep](https://gafferongames.com/post/fix_your_timestep/)).
- Fast-forward just means more ticks per frame. Target 2 ms or less per tick at end-game scale; that leaves room for roughly 8x speed at 60 fps.

**Commands are the only way to change state.** Each command has `check(state) -> cost | error` and `apply(state)`.
- OpenTTD runs every command once as a test and then for real (`DC_EXEC`), so cost previews come for free ([command_func.h](https://sources.debian.org/src/openttd/14.1-1/src/command_func.h)).
- A log of tick + command, plus the seed and a content hash, gives you replays, exact bug reproduction and AI players that use the same API ([Game Programming Patterns](https://gameprogrammingpatterns.com/command.html)).

**Determinism (same seed and commands always give the same game).**
- Money is integer cents; positions and speeds are fixed-point integers. Floats from numpy and the C math library are not bit-identical across machines ([xsuite](https://xsuite.readthedocs.io/en/latest/_sources/numericalreproducibility.rst.txt)).
- Python only promises that `Random.random()` keeps its sequence across versions; `randrange`, `choice` and friends may change ([docs](https://docs.python.org/3/library/random.html)).
- numpy's `Generator` only promises the same stream on the same build and machine ([NEP 19](https://numpy.org/neps/nep-0019-rng-policy.html)).
- So wrap `random()` in your own `SimRng` (36 ns per draw measured here). Use one stream per subsystem and store its state in the save.
- Never loop over a `set` of strings; its order changes between runs.
- Factorio checksums the whole game state every tick and replays games to find where two runs diverge ([FFF #47](https://factorio.com/blog/post/fff-47)). Build the same as a test tool.

**Not ECS.** esper 3.9 and tcod-ecs 5.5.2 are maintained, but a tycoon game has few, stable entity types. Its hard questions are about location and relationships ("which industries are near this station"). Instead:
- Store entities as `@dataclass(slots=True)` objects in registries keyed by integer ID.
- Refer to other entities by ID, not object reference. Saves stay simple and there are no reference cycles for the garbage collector.
- Systems are plain functions, run in a fixed order.
- Use numpy arrays for bulk data: tiles, stock per station and cargo, demand between station pairs.
- Record monthly statistics in numpy ring buffers that go into the save. The in-game charts and the balancing tools both read these.

**Saves.**
- msgspec typed structs, encoded as MessagePack and compressed with the stdlib `compression.zstd` (new in 3.14, [docs](https://docs.python.org/3/library/compression.zstd.html)).
- A header with format version, content hashes, tick and seed.
- A chain of `vN -> vN+1` migration functions, following msgspec's rules for evolving schemas ([guide](https://msgspec.pages.dev/schema-evolution.html)). OpenTTD does the same with `SaveLoadVersion` ([saveload.h](https://docs.openttd.org/source/d6/dd4/saveload_8h_source)).
- Keep old save files as test fixtures.
- **Pickle is a dealbreaker.** Loading a pickle can run arbitrary code, and it stores classes by module path, so renaming or moving a class breaks old saves ([docs](https://docs.python.org/3/library/pickle.html)).

**Content.**
- Load TOML files with `tomllib` into pydantic models.
- Validators check cross-references (unknown cargo IDs) and loops in upgrade trees (stdlib `graphlib`).
- Compile the result into read-only tables indexed by integer ID, and export a JSON Schema for modders.
- City and building evolution rules stay declarative; never `eval` mod content.

## 2. Graphs and routing

The rail network is stored in four layers:
1. Track pieces per tile, in a numpy array.
2. A track graph that knows direction (trains cannot reverse at switches).
3. A condensed graph: runs of plain track are merged into single segments, segment costs are cached, and only segments touched by construction are rebuilt. OpenTTD's YAPF pathfinder does the same ([CYapfRailSegment](https://docs.openttd.org/source/d8/df8/structCYapfRailSegment.html)).
4. One station graph per cargo type, built from the routes trains actually run.

Measured on this M3 Pro with CPython 3.13.0 and `heapq`:

| Query | Time |
|---|---|
| Full Dijkstra, 10k nodes / 40k arcs | 4.2 ms |
| A* from corner to corner, same graph | 6.9 ms |
| Shortest paths between all pairs of 300 stations | 57 ms |

- **Hand-written A\*** on layer 3 for train routing, because you need custom costs (signals, reserved track, slopes).
- **rustworkx 0.18.1** for station-graph work. It has prebuilt wheels and uses integer node IDs ([guide](https://www.rustworkx.org/networkx.html)). A third-party benchmark shows Rust graph code 12-23x faster than networkx on all-pairs Dijkstra ([rust-graph](https://pypi.org/project/rust-graph)).
- **networkx 3.7** only to check your A* in tests and for notebooks.
- **igraph 1.0.0** is a poor fit: it is built for graphs that do not change, adding edges one at a time is slow ([forum](https://igraph.discourse.group/t/igraph-is-much-slower-than-networkx-when-generating-a-graph/853)), and it has had no release in 12 months.

**Cargo with destinations.** OpenTTD's cargodist solves a multi-commodity-flow problem for each connected part of the network, in background threads that rejoin the game at fixed times. Its docs describe the solver as CPU-heavy and exponential in the number of stations, tuned by recalculation interval, time and accuracy settings ([linkgraph.md](https://github.com/OpenTTD/OpenTTD/blob/master/docs/linkgraph.md), [wiki](https://wiki.openttd.org/en/Manual/Passenger%20and%20cargo%20distribution)). To keep it cheap:
- Route between stations only, never tiles.
- Model demand with a gravity formula (bigger, closer places attract more cargo), limited to the top-N destinations per station.
- Group cargo into (origin, destination, cargo) batches instead of individual units.
- Store a next-hop table per station, so each loading decision is a single lookup.
- Recompute only the parts of the network that changed. Spread the work over ticks, or run it in a worker and apply the result at a fixed later tick.
- Start with destinations for passengers and mail only.

## 3. Performance headroom

**Python versions.**
- 3.15.0 shipped on 2026-10-09. Current releases are 3.15.2 and 3.14.10, and 3.13 now gets security fixes only ([python.org](https://www.python.org/downloads/)). Your machine has 3.13.0.
- The JIT compiler is still experimental. In 3.15 it gives 11-12% on Apple Silicon Macs ([What's New 3.15](https://docs.python.org/3.15/whatsnew/3.15.html)). The 3.14 installers include it, switched on with `PYTHON_JIT=1`.

**Budget, measured on one core:**

| Operation | Time |
|---|---|
| Train update (movement plus signal check) | 265 ns per train; 1.3 ms for 5,000 trains |
| Industry production step | 170 ns |
| Monthly update of 1,000 cities x 20 cargo types | 0.9 ms |

Assume real code is 3-5x slower. Then a 2 ms tick fits about 1,000-2,000 trains, tens of thousands of buildings updated in turns, and hundreds of stations. That is comfortably Railroad Tycoon 2 scale; OpenTTD scale needs the steps below.

**When to escalate.** Profile first, then go down this list:
1. Better algorithms: spread work over ticks, cache, condense graphs. Always needed.
2. numpy 2.5.4 for the same calculation over many items.
3. rustworkx once a routing pass takes more than about 50 ms.
4. mypyc or Cython 3.3.1 when the slowness is spread over many small Python classes and functions. mypyc compiles type-annotated Python to C. It is alpha, gives 1.5-5x, and needs a rebuild per Python version ([intro](https://mypyc.readthedocs.io/en/latest/introduction.html)).
5. numba 0.68.1 for heavy numeric loops with branches. Downsides:
   - about 40 MB of llvmlite per platform ([files](https://pypi.org/pypi/llvmlite/0.50.0/json))
   - a compile pause the first time each function runs
   - its ahead-of-time compiler is deprecated with no replacement ([notice](https://numba.readthedocs.io/en/latest/reference/deprecation.html))

   Prefer it in batch tools, not the shipped game.
6. Rust via PyO3 0.30.1 and maturin 1.16 for the last one or two hot spots (A*, flow solver, train movement). This gives the biggest speedup but means learning Rust.

PyPy 7.3.23 (Python 3.11) could speed up headless batch runs, but not the shipped game; the packagers target standard CPython.

## 4. Testing and balancing

**Stateful property tests** with pytest 9.2 and hypothesis 6.170's `RuleBasedStateMachine` ([docs](https://hypothesis.readthedocs.io/en/latest/stateful.html)). Hypothesis generates random sequences of player commands and "advance N ticks", and after each step these must hold:
- Every money transfer is recorded as a matching debit and credit, so all accounts sum to zero.
- For each cargo type: produced = consumed + delivered + in transit + in stock + spoiled.
- No stock is ever negative, and no train carries more than its capacity.
- The same seed and commands always produce the same state hash.
- Saving, loading and then stepping gives the same result as just stepping.

Also check your A* against networkx shortest paths on random graphs.

**Golden runs.** Run 3-5 fixed scenarios with fixed seeds and a scripted bot for 50 in-game years. Save yearly statistics and the state hash as snapshots with syrupy 6.1.1. Run them on both macOS and Windows and compare the hashes.

**Balancing.**
- A headless `sim.batch` command runs 100+ seeds across a grid of parameter values in a process pool and writes Parquet files.
- Analyse with polars 2.1 (pandas 3.1.1 also works) and matplotlib in Jupyter. Compare the 10th percentile, median and 90th percentile across seeds, not single runs.
- Cities growing from deliveries is a self-reinforcing loop. Design growth to level off (logistic, S-shaped curve) and add tests that growth rates stay bounded.

## Genre mechanics, open-source reference implementations, and the technical requirements they imply (mechanics)


### Key findings

- OpenTTD (15.3 stable, 16.0-RC1 released 2026-10-31, commits today) and Simutrans (125.0.1, 2026-10-05) are both very actively maintained C++ codebases worth reading. They are GPL-2.0 and Artistic-licensed, so re-implement their mechanics rather than porting code.
- Vanilla OpenTTD town growth ignores how much and which cargo is delivered: it counts up to 5 stations that handled any cargo in about 50 days. That makes it the wrong model for the signature mechanic.
- The right models for city evolution are TF2 building levels that add second and third cargo demands, Anno tiers unlocked by meeting needs, and Simutrans industry chains that spawn at 2^n × N inhabitants.
- OpenTTD's payment formula (rate × units × Manhattan distance × time factor falling from 255 to 31, in 2.5-day periods) is a proven baseline. Adding RT2-style destination demand that is used up by deliveries and recovers over time links growing cities to profit and pushes players to build wider networks.
- Service-quality feedback must be smoothed. OpenTTD moves station ratings at most ±2 points per 2.5 days and changes industry output with a 1/22 monthly chance biased by the share transported (60%/80% thresholds). Copy that approach: moving averages, caps, and separate up/down thresholds so cities don't oscillate.
- Start passenger and mail destinations with Simutrans-style origin-destination generation (gravity weighting, route check at generation, 'no route'/'overcrowded' stats feeding growth). Add cargodist-style capacity-aware routing later; even OpenTTD ships cargodist turned off.
- TF2 simulates every resident and cargo item as an agent; doing that in Python is a dealbreaker. Use aggregated origin-destination tables and merged cargo buckets instead.
- Recommended representation: a NumPy tile grid (about 512×512) for terrain, land use and catchment, plus a derived track graph for movement, signals and pathfinding. Spline-based freeform track (TF2) is too costly for a first game.
- Measured in pure CPython 3.13 on this M3 Pro: about 0.25 µs per minimal train update, 1.1 ms per A* query and 2.9 ms per full Dijkstra on a 5k-node graph, 58 ms for all-pairs routes over 300 stations. So 500–1,000 trains and about 300 stations are feasible if routing is cached and periodic.
- Genre timing is about 2 s per game day at 1× (OpenTTD and TF2). Use about 24 fixed ticks per day with daily and monthly schedulers, spread entity updates across ticks, keep the calendar clock separable, and use time-slicing or a worker process rather than threads for heavy routing.

# Genre mechanics, reference code and derived technical requirements

Checked 2026-11-05. **Verdict:** read OpenTTD and Simutrans for the economy core, but do not copy vanilla OpenTTD's town growth, because it ignores how much cargo arrives. The signature mechanic needs a blend of Transport Fever 2 (TF2) building levels, Anno-style tiers and Simutrans industry spawning, smoothed the way OpenTTD smooths its feedback loops. Python is fast enough for the simulation at Railroad Tycoon 2 (RT2) scale if routing runs periodically and per-tick work is only train movement.

## 1. Cargo pricing
- **OpenTTD** ([economy.cpp `GetTransportedGoodsIncome`](https://github.com/OpenTTD/OpenTTD/blob/master/src/economy.cpp), [wiki](https://wiki.openttd.org/en/Manual/Game%20Mechanics/Cargo%20income)):
  - Income = rate × units × Manhattan distance between the two stations × time factor ÷ 2^21.
  - Time factor = 255 − max(0, t−d1) − max(0, t−d1−d2). It is floored at 31, then decays towards 1 for extremely slow deliveries.
  - t is counted in 2.5-day periods. For passengers d1=0 and d2=24.
  - Payment rates inflate monthly.
- **RT2:** revenue also depends on demand, economic state (5 states, boom to depression) and station improvements ([Wikipedia](https://en.wikipedia.org/wiki/Railroad_Tycoon_II)). On the expert model, station demand (0–7) collapses after a few large deliveries and recovers slowly. High demand pays about 2× ([Steam](https://steamcommunity.com/app/7620/discussions/0/1726450077651430540)).
- **RT3:** prices form a field across the map. Carloads drift down the price gradient even without rail, and revenue is the price difference ([Wikipedia](https://en.wikipedia.org/wiki/Railroad_Tycoon_3)).
- **Use:** OpenTTD's distance × time decay, multiplied by an RT2-style destination demand that is used up by deliveries and recovers over time. The demand term is what ties evolving cities to money.

## 2. Production and service quality
- **OpenTTD station rating** ([station_cmd.cpp](https://github.com/OpenTTD/OpenTTD/blob/master/src/station_cmd.cpp)):
  - Starts at −90.
  - Adds up to +130 for time since last pickup and up to +130 for little cargo waiting (thresholds 1500/1000/600/300/100 units).
  - Adds (speed−85)/4, up to +42; +33 for a new vehicle; +26 for a statue.
  - Moves at most ±2 points per 2.5 days.
  - Cargo handed to stations = amount × (rating+1)/256, split among competing stations. Low ratings delete waiting cargo.
- **OpenTTD smooth economy** ([industry_cmd.cpp](https://github.com/OpenTTD/OpenTTD/blob/master/src/industry_cmd.cpp)):
  - Each month, each output has a 1/22 chance to change by 4–23%.
  - Chance that the change is an increase: 1/3, 2/3 or 5/6 when last month's transported share was ≤60%, ≤80% or >80%.
  - An industry closes when every output is at the minimum rate.
- **Simutrans** ([simfab.cc](https://github.com/simutrans/simutrans/blob/master/src/simutrans/simfab.cc)):
  - Each factory has fixed links to consumer factories, and goods are assigned a consumer only if a route exists.
  - A full output store stops production.
  - Deliveries of power, passengers and mail raise output.
- **TF2** ([wiki](https://www.transportfever2.com/wiki/doku.php?id=gamemanual:industriescargos)):
  - Processing capacity steps between 100 and 400, moving up or down based on deliveries.
  - Cargo goes to consumers the player's lines can reach.
  - New industries spawn to keep a density target. Idle industries close after 10 years plus a 730-day countdown.
- **FIRS** (an OpenTTD industry add-on, [wiki](https://wiki.openttd.org/en/Community/NewGRF/FIRS)): processing output rises with the *variety* of inputs delivered in about 30 days. This is a cheap way to reward richer networks.

## 3. Town growth and city evolution
- **OpenTTD is the counter-example** ([town_cmd.cpp](https://github.com/OpenTTD/OpenTTD/blob/master/src/town_cmd.cpp), [Towns](https://wiki.openttd.org/en/Manual/Towns)):
  - The growth interval comes from a fixed table {320,420,300,220,160,100}, indexed by the number of "active" stations (any cargo in about 50 days, capped at 5).
  - That value is halved at normal speed, halved again for cities, and divided by (houses/50+1). Unserved towns grow in only 1 of 12 months.
  - In practice a small town gets one building attempt about every 48 days with 5 stations, or every 200 days with 1. A 200-house town with 5 stations gets one about every 10 days.
  - Quantity and variety don't count, except at least 1 unit of food or water in snow or desert towns. That is why scripts like [Renewed Village Growth](https://github.com/F1rrel/RenewedVillageGrowth) exist: they make growth depend on varied cargo categories.
- **Simutrans** ([simcity.cc](https://github.com/simutrans/simutrans/blob/master/src/simutrans/world/simcity.cc)):
  - Monthly growth is proportional to transported ÷ generated for passengers, mail and goods. The weights are configurable (historically 40/20/20).
  - The result is divided by a size-class factor (below 1,000, below 10,000, larger).
  - A new industry chain spawns when a city passes 2^n × `industry_increase_every` inhabitants, e.g. at 5k/10k/20k/40k ([forum](https://forum.simutrans.com/index.php?msg=82400)).
  - **This is the closest existing match to the requested mechanic.**
- **TF2** ([Towns](https://www.transportfever2.com/wiki/doku.php?id=gamemanual:towns)):
  - Towns have residential, commercial and industrial districts.
  - Growth comes from reachable destinations plus cargo supply (up to +100% per district). Overcrowding, traffic and emissions reduce it.
  - Level 1–2 buildings demand one cargo; levels 3–4 add a second or third.
- **Anno** ([PC Gamer](https://www.pcgamer.com/au/anno-1800-tips-guide), [Steam](https://steamcommunity.com/app/916440/discussions/0/4626978782935270832)):
  - Houses fill up as needs are met. Meeting basic needs allows an upgrade to the next tier.
  - Each tier brings new needs and the workforce that new production buildings require.
  - A Python implementation exists: Unknown Horizons' [`settler.py`](https://github.com/unknown-horizons/unknown-horizons/blob/master/horizons/world/building/settler.py) (happiness thresholds, min/max inhabitants per tier, upgrades consume materials, houses decay to ruins).
- **Design for this game:**
  - City tier = f(population, sustained satisfaction of that tier's needs).
  - Building types are defined in data files, and their demands widen as their level rises (TF2).
  - Moving up a tier unlocks new building and industry types (Anno) and spawns a processing industry (Simutrans).
  - Smooth everything: 3–6-month moving averages, a gap between tier-up and tier-down thresholds so cities don't flip back and forth, and a cap on growth per month.

## 4. Passenger and mail destinations
- **OpenTTD cargodist** ([wiki](https://wiki.openttd.org/en/Manual/Passenger%20and%20cargo%20distribution), [mcf.cpp](https://github.com/OpenTTD/OpenTTD/blob/master/src/linkgraph/mcf.cpp), [settings](https://github.com/OpenTTD/OpenTTD/blob/master/src/table/settings/linkgraph_settings.ini)):
  - Builds a network of station-to-station links per cargo.
  - Assigns demand symmetrically or asymmetrically, with distance effect 100% and accuracy 16.
  - Routes it with a two-pass multi-commodity flow: Dijkstra at 80% saturation, then widest-path, then cycle removal. The result is a next-hop share table at each station.
  - Runs in threads, started every 8 s with 32 s allowed. **It is off by default.**
- **Simutrans** ([simhalt.cc](https://github.com/simutrans/simutrans/blob/master/src/simutrans/simhalt.cc)):
  - The destination is chosen when passengers are generated, weighted by population and distance.
  - Passengers travel in packets of 7.
  - Routes are found with Dijkstra over transfer stops (cost 8 per wait plus 1 per stop, with limits on transfers and hops).
  - The outcome (OK, walked, overcrowded, no route) feeds city statistics.
  - Connection rebuilding is spread over ticks in 1,024-unit chunks.
- **Simutrans-Extended** ([passengers](https://www.wiki.simutrans.com/en_extended_Passengers), [path_explorer.h](https://github.com/jamespetts/simutrans-extended/blob/master/path_explorer.h)): routes by journey time, and passengers refuse trips over their time tolerance. It computes all-pairs Floyd–Warshall per cargo category, spread over many ticks, with a working copy and a finished copy.
- **TF2** simulates every resident and cargo item as an individual agent ([overview](https://www.transportfever2.com/wiki/doku.php?id=gamemanual:simulationoverview)). **This is a dealbreaker model for Python.**
- **Use:** start with Simutrans-style origin–destination generation; add cargodist-style capacity-aware routing later.

## 5. Catchment, track, finance
- **Catchment radii** (OpenTTD, [station_type.h](https://github.com/OpenTTD/OpenTTD/blob/master/src/station_type.h)): 3 tiles for bus/truck stops, 4 for rail, 5 for docks, up to 10 for airports. A cargo counts as accepted at 8/8 acceptance.
- **Signals and pathfinding:**
  - OpenTTD progresses from block signals to pre-signals to path signals, which reserve a route to a safe waiting point ([Signals](https://wiki.openttd.org/en/Manual/Signals)).
  - Its YAPF pathfinder caches segment costs and clears the cache when a global track-change counter increments ([yapf/](https://github.com/OpenTTD/OpenTTD/tree/master/src/pathfinder/yapf), `pbs.cpp`, `signal.cpp`).
  - The JGR patchpack adds realistic braking, scheduled dispatch and programmable signals ([repo](https://github.com/JGRennison/OpenTTD-patches)).
- **Finance:**
  - RT2 had bonds whose rates follow the economic climate, stock issues and buybacks, dividends, trading in any company's shares, mergers and bankruptcy.
  - OpenTTD 14 replaced share trading with hostile takeovers of AI companies ([changelog](https://newreleases.io/project/github/OpenTTD/OpenTTD/release/14.0-beta1)). Its default loan is 300,000 at 2%.
  - A stock market only matters with AI rivals, so it belongs in a later phase.

## 6. Technical requirements
**Map representation (hybrid):**
- A NumPy tile grid for terrain, city footprints, catchment and track laying snapped to 8 directions. At 512×512 (262k tiles) this is about 1–3 MB.
- A **track graph** derived from it: nodes are junctions, signals and platform ends; edges carry length, speed limit, grade and reservation state. Update it incrementally and use it for movement, signals and pathfinding.
- For comparison, OpenTTD maps run from 64 to 4,096 tiles per side ([source](https://wiki.openttd.org/en/Archive/Manual/Settings/Map%20size)), and TF2 uses 8–16 km maps with curved (spline) tracks. **Splines are too costly for a first game.**
- Don't loop over every map tile each tick in Python, as OpenTTD does (it processes map/256 tiles per tick). Iterate over buildings and other entities instead, spreading the work across days.

**Entity envelope for v1:**

| Entity | Target | OpenTTD reference |
|---|---|---|
| Towns | 30–60 | ~23 per 256² map on normal |
| Industries | 100–200 | 55 per 256² map on normal |
| City buildings | 10k–30k | |
| Stations | 100–300 | |
| Trains | 200–1,000 | default cap 500 per company |
| Track graph nodes | 2k–10k | |
| Cargo types | 15–25 | |
| Cargo buckets | 10k–50k | packets merged when source/age/first station match; pool ≈16M |

**Time model:**
- About 2 s per game day at 1×, the genre norm (OpenTTD: 74 ticks × 27 ms; TF2: 2 s).
- 24 fixed ticks per day (12 Hz at 1×, 192 Hz at 16×), with interpolated rendering. Process every edge crossing within a tick so coarse ticks don't skip signals.
- Station and cargo updates daily; growth, production and finance monthly; routing every 4–16 days.
- Keep the calendar clock separate from the economy clock so eras can progress at a different speed (OpenTTD 14 did this, [news](https://www.openttd.org/news/2024/03/23/timekeeping)).

**Hot paths** (pure-Python micro-benchmarks run here: M3 Pro, CPython 3.13.0):

| Work | Measured | Implication |
|---|---|---|
| Train kinematics + reservation check | 0.25 µs per train per tick | 1,000 trains at 16× ≈ 0.05 s CPU per second; plan 1–2 µs with full logic (0.2–0.4 s) |
| A* on a 5k-node graph | 1.1 ms per query | Pathfind only at junctions; cache by (node, destination); clear on track changes |
| Full Dijkstra, 5k nodes | 2.9 ms | Precomputing distances to each destination is feasible |
| All-pairs routes, 300 stations | 58 ms | Periodic, time-sliced passenger/cargo routing is fine |
| 54k cargo buckets per day | 2.7 ms | Store cargo as aggregated counts, never per unit |

CPython threads don't run Python code in parallel, so cargodist-style background threads won't help. Spread jobs over ticks (Simutrans) or use a worker process. If graphs grow, move to SciPy's csgraph or rustworkx.

**Must live in data files:**
- Cargo specs: rate, d1/d2, class, weight.
- Industry recipes and capacity levels.
- Building types: tier, residents and jobs, cargo produced and demanded per level, unlock rules.
- Tier thresholds and needs.
- Vehicles, track and signal types.
- Economy constants: inflation, economic-climate transition probabilities, interest.
- Growth weights and smoothing constants.
- Scenarios.

**Minimal prototype (headless first):**
- 256² map, 8–10 towns with 3 tiers.
- About 20 industries in 3 chains: coal + iron → steel → goods; grain → food; wood → lumber. 7 cargo types including passengers and mail.
- Track graph with block signals; trains running point-to-point orders.
- OpenTTD-style payment × demand pools; station rating; smooth production changes; ratio-based growth with tier unlocks and industry spawning.
- Loan, interest and maintenance ledger.
- Seeded random numbers and integer money.
- 50 simulated years in under a minute, exported as CSV and plots; tests that cargo and money are conserved.
- Defer destination routing, path signals, stocks and AI.
